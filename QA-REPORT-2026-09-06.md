## Major

1. **A missed 5 s handshake window is sticky until the next reconnect.**
   `settle()` in `src/extension/daemon-verification.ts` is first-wins by
   design (so a late `auth.ok` cannot flip a verdict callers acted on). The
   consequence I did not weigh properly: if the exchange overruns 5 s for a
   benign reason (EasyEDA's main process busy, so the token read over IPC
   stalls; or the daemon's event loop busy), the gate settles `unverified`,
   a toast blames a rogue listener, every request is refused, and **nothing
   recovers** until the socket drops and `connect()` calls `reset()`. The
   extension does not reconnect on its own while the socket is healthy, so
   the user must Disconnect/Connect Claude or restart the daemon.
   Evidence: 10 of 10 field handshakes completed in under 10 ms, so
   likelihood is low; blast radius is one manual reconnect. Still a
   self-inflicted failure mode in the primary path.
   Where: `daemon-verification.ts:84-99` (`settle`), `ws-client.ts`
   `handleAuthOk`.
   Fix: let a **MAC-verified** `auth.ok` upgrade `unverified` to `verified`
   (a rogue cannot forge it, so the upgrade is safe; only the timeout and
   bad-MAC cases should remain sticky against each other), log "verified
   late", and show a second toast so the first is not left standing. Raising
   the window to 15 s is a reasonable belt-and-braces addition; it delays
   flagging a silent rogue by 10 s and costs nothing on the happy path.

2. **Residual, unchanged from 1.6.0 and by design: the token-unreadable
   posture is still Origin-trust.** Browser build, or desktop with the
   external-interaction permission off, yields `not-applicable` and requests
   run against an unverifiable peer. Recorded so the accepted risk stays
   explicit; the README says so. No action unless Ben wants `require`-style
   refusal on the extension side too.

## Minor

1. **Refusal reason after a reconnect is misleading.** `reset()` wakes any
   waiter from the old socket with `idle`, and the pipeline then reports
   "no auth.challenge was received on this connection". True of the new
   socket, wrong about what happened. Cosmetic: the daemon has already
   rejected that request on socket close, so the response is dropped.
   Fix: have `reset()` wake waiters with a distinct value (or the pipeline
   check `isConnected()` first) and log "connection reset mid-request".

2. **Extension-side gate wiring is verified by review and field log only*.**
   The state machine has 9 unit tests and the daemon side has an e2e test
   (including the new `auth.ok`-before-`hello` order), but `ws-client.ts`
   itself cannot run headless (ambient `eda`). The field record is the
   evidence. A thin `eda` stub harness for `handleMessage` would close this;
   it is the same gap the 2026-07-24 work order chose not to build.

3. **In-place log rotation is unexercised*.** Code path read again: fd 2 is
   the O_APPEND log file under `spawn.ts`, `fstat` inode guard is correct,
   `copyFileSync` then `ftruncateSync(2, 0)` is the right sequence, and a
   test pipe is correctly skipped. Two weeks produced 462 KB, so it will be
   months before it fires in normal use. To exercise it deliberately:
   `dd if=/dev/zero bs=1m count=6 >> ~/.easyeda-mcp/bridge.log`, then any
   256 log lines (a few `server_info` calls will not do it; a reconnect
   cycle or a netlist fetch will), then check for `bridge.log.1`.

4. **No PROJECT.md.** The qa skill asks for the outcome to be recorded
   there; this repo's convention is dated `QA-REPORT-*.md` files, which is
   what this is. Fine, but say so somewhere a new session will look
   (HANDOVER.md "State" section) so the next agent does not create one.

5. **Branch is 17 commits ahead of `sheares/main` and has no upstream of
   its own.** Nothing pushed, per ground rules. Noting only because the
   v1.6.1 `.eext` is installed and in daily use while the code that built
   it exists in exactly one working tree.
