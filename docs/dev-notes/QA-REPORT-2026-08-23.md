## Major

1. **No layer reports its version on the tool surface.** `server_info`
   returns port, instances and `allowAllOrigins` but no daemon, extension or
   proxy version; the daemon never learns the extension's version (the
   extension only shows it in its About dialog). The work order's live check 1
   ("`server_info` confirms … the new version") therefore cannot be performed.
   This matters here more than usual: the daemon stays resident across
   rebuilds as long as any MCP client holds it open (the current one has run
   since 2026-08-10 with six to seven clients attached), and EasyEDA treats a
   same-version `.eext` reinstall as a silent no-op, so three-layer version
   drift is a realistic state that nothing can currently detect.
   Where: [`src/bridge-daemon/tools/builtin-tools.ts:13-37`](../../src/bridge-daemon/tools/builtin-tools.ts:13),
   [`src/extension/index.ts:82`](../../src/extension/index.ts:82).
   Fix: reuse the Q6 esbuild define for the daemon bundle and add
   `daemonVersion` to `server_info`; have the extension include
   `extensionConfig.version` in its `instanceInfo` push and surface it per
   instance. Ten lines, no protocol break (older extensions just omit it).

2. **WP11 spec gap: a missing `auth.ok` is never detected.** The work order
   required the "unverified daemon" warning on `auth.ok` failure **or
   absence**. `handleAuthOk` handles failure; nothing handles absence. A rogue
   listener that copies the genuine `auth.challenge` shape (`scheme:
   'hmac-v1'` plus a nonce) receives a harmless HMAC answer, never sends
   `auth.ok`, and the extension stays silently unverified while executing
   every handler it is sent. The same applies to a peer that sends no
   challenge at all. Because verification is advisory (finding 3), this gap
   removes the only signal the user would get.
   Where: [`src/extension/ws-client.ts:557-613`](../../src/extension/ws-client.ts:557).
   Fix: when `answerAuthChallenge` sends an hmac answer, arm a short timer
   (about 5 s) that calls `warnUnverifiedDaemonOnce('daemon never completed
   mutual auth')` if `isDaemonVerified()` is still false; arm a similar timer
   on connect for the no-challenge case. Clear both in `handleAuthOk`.

3. **Accepted-risk item, by design: handlers are not gated on daemon
   verification.** D1 is now detected (when finding 2 is fixed) but not
   prevented; `isDaemonVerified()` exists and is unused by the request
   pipeline. The work order explicitly deferred this to Ben. Recording it so
   the ship decision is explicit: the local-attacker scenario (another OS
   account binding 16168 during a daemon-down window) still yields full
   read/write access to open designs for as long as the user ignores the
   toast.
   Fix when decided: in `handleMessage`, refuse write-class methods (or all
   methods) while `!isDaemonVerified()` and the token was readable, with a
   clear error.

4. **Unverified: WP1 on symbol and footprint editor tabs (doctype 2 and
   4).** The work order asked for this path to be verified; the commit does
   not claim it was, and the permissive fall-through only triggers when
   `getCurrentDocumentInfo()` lacks both `uuid` and `tabId`. If a library
   editor tab reports either field in a different shape, every request routed
   to it fails closed with a "switch verification failed" error. Not a data
   risk (fail-closed), but potentially a broken feature. I could not test it:
   `lib_symbol_open_in_editor` on a system-library symbol returned `false`
   without opening anything (see Minor 2). Needs a live check with a
   personal- or project-library symbol open; see the list at the end.

## Minor

1. **The `.eext` ships the two QA reports.** `.edaignore` excludes `AUDIT.md`
   and `HANDOVER*.md` but not `QA-*.md`, so `QA-REPORT-2026-07-24.md` and
   `QA-DEEP-REPORT-2026-07-24.md` (38 KB together) are inside
   `easyeda-agent-mcp-server_v1.6.0.eext`. Add `QA-*.md` to `.edaignore`
   (this file will otherwise ship in 1.7.0 too).

2. **`lib_symbol_open_in_editor` returns a bare `false` on failure.** The
   description promises "Returns the new tabId"; the handler passes the SDK
   boolean straight through, so a caller gets `false` with no error and no
   reason. Where: [`src/extension/handlers/library.ts:65-66`](../../src/extension/handlers/library.ts:65).
   Fix: throw when the result is not a string, and say in the description
   that system-library symbols may not be openable this way.

3. **`requireDocumentType` errors carry a renderer stack trace**, including
   the `modules.lceda.cn/pro-api/...` URL. Noise for the model, and a few
   hundred wasted tokens per miss. Where: `describeError` on the
   `requireDocumentType` throw path in `ws-client.ts`. Fix: return
   `err.message` only for this known, deliberate error.

4. **D6 log rotation only runs at spawn.** `rotateLogIfLarge` is called
   before `openSync` in `spawn.ts`, so a resident daemon's log is unbounded
   between spawns. Today's daemon is 13 days old with a 430 KB log, so the
   practical risk is low, but the documented 5 MB cap is not a cap. Either
   accept and say so in the README, or check size inside the daemon's own
   `log()` every N writes.

5. **`HANDOVER-2026-07-24.md` is stale in two places.** Line 23 still says
   "Propose-only: nothing in this document has been implemented"; everything
   has. And live check 7's optional step ("toggle the permission off …
   confirm the toast DOES appear") contradicts the code and the work order's
   own rule: with the permission off the token is unreadable and the toast is
   deliberately suppressed. The implementing session also left no closing
   note file (the commit bodies carry the information). Add a two-line
   "Implemented in commits 8721c83..b2bee8e" header and correct check 7.

6. **No hard response-size cap, and some read tools lack `fields`/`limit`.**
   `pcb_get_design_rules` returns about 9 KB with no way to narrow it;
   `document_get_source` can return multi-MB payloads. Known and documented in
   the description text, but worth a daemon-side byte cap with a
   "truncated, use fields/limit" note. Deferred Q11-style work; noting so it
   is not forgotten.

7. **Tool-list size.** The 100 descriptors total about 150 KB (~37k tokens)
   if a client loads every schema eagerly. Claude Code defers MCP schemas so
   this is not felt there; other clients may feel it. `sch_swap_supplier_part`
   (4.3 KB) and the two export tools (3.3 to 3.8 KB) are the longest.

8. **Multi-page swap backup fallback is silent.** When `resolveProjectUuid`
   fails, `sch_swap_supplier_part` with `allSchematicPages` takes a single-
   document backup while still walking every page. `formatBackupSummary`
   (`backup.ts:124`) only exposes this implicitly through the `path` field;
   add an explicit "project uuid unavailable; only the active document was
   snapshotted" sentence to the note in that branch.
