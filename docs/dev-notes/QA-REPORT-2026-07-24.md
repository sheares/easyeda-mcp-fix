## High

### Q1. The per-request `document` switch is never verified

`src/extension/ws-client.ts:355-359` awaits `switchToDocument(document)` and
discards its return value. The only post-switch gate is
`requireDocumentType()` (`ws-client.ts:220-243`), which checks the *type* of
the active document (1 = schematic, 3 = PCB) and nothing else.

`dmt_EditorControl.openDocument` can fail without throwing. This repo already
says so, in its own words, at `src/extension/handlers/sch-page-walk.ts:14-17`:
"a failed open leaves the previous page active, and re-reading it would
silently duplicate that page's primitives". `forEachSchematicPage` therefore
verifies every open against `getCurrentSchematicPageInfo()` and aborts on
mismatch. The primary request path, which is the one that carries every write
tool, has no equivalent check.

Failure mode: a project holding more than one PCB (the comment at
`src/extension/handlers/sch-component.ts:191-193` records exactly this shape,
"Splitflap Board1/2/3 in one project"). A request targeting Board 3's PCB
whose `openDocument` silently no-ops leaves Board 1's PCB active. Both are
`documentType: 3`, so the type gate passes, and `pcb_delete_primitives`,
`pcb_create_track` or `pcb_move_component` then execute against the wrong
board. The backup taken by the delete tools snapshots the document the
*daemon* thinks is active, so it does not protect the board that actually
gets modified.

The fix is the same shape as the page-walk guard, and the data needed is
already available: `dmt_SelectControl.getCurrentDocumentInfo()` returns both
`uuid` and `tabId`, and `editor.getOpenTabs` (`handlers/editor.ts`) already
demonstrates the `tabId.startsWith(uuid)` relationship.

### Q2. `sch_swap_supplier_part` is the only bulk mutation with no backup

`src/bridge-daemon/tools/sch-write-tools.ts:164-198`. The tool writes supplier
metadata to every component matching a filter, optionally across every
schematic page, and never calls `backupDocument` or `backupProject`.

Every other document-destructive tool snapshots first:

- `sch_delete_component` — `sch-write-tools.ts:128`
- `sch_delete_wire` — `sch-write-tools.ts:236`
- `pcb_delete_primitives` — `write-tools.ts:265`
- `document_set_source` — `file-manager-tools.ts:150`
- `document_load_from_file` — `file-manager-tools.ts:218`
- `project_import_file` — `file-manager-tools.ts:267`

So the highest-blast-radius write in the surface is the one exception. This is
also precisely the failure class the fork was built for: the README's opening
paragraph records "twenty-four components lost their BOM lines in one batch
before the pattern was noticed".

Compounding it, with `allSchematicPages: true` the write happens inside
`forEachSchematicPage`, which throws and aborts the walk if any page fails to
open (`sch-page-walk.ts:44-48`). Pages already visited keep their new
metadata; there is no snapshot to compare against and no transaction to roll
back. `dryRun` mitigates by convention only.

### Q3. No MCP tool annotations anywhere in the surface

`ToolDescriptor` (`src/bridge-daemon/protocol.ts`) carries `name`,
`description` and `inputSchema` and nothing else. `ToolRegistry.makeDescriptor`
(`registry.ts`) builds exactly those three fields, and
`mcp-server/index.ts:77-84` passes only `description` and `inputSchema` to
`server.registerTool`. Confirmed by grep: no occurrence of `readOnlyHint`,
`destructiveHint`, `idempotentHint` or `openWorldHint` anywhere in `src/`.

Tool annotations are the mechanism MCP clients use to decide what may run
without a human checkpoint. Current 2026 guidance is explicit that agents
should not be able to execute destructive or irreversible operations without
an approval step, and that risk classification belongs on the tool descriptor
rather than in prose. As shipped, roughly 60 pure reads (`sch_get_*`,
`pcb_get_*`, `lib_get_*`, `editor_get_*`) are indistinguishable at the
protocol level from `pcb_delete_primitives` and `document_set_source`. A
client that offers "auto-approve read-only tools" cannot help this server, and
one that prompts on everything trains the user to click through.

This is cheap to add and the highest-leverage change on the list: one optional
field on `ToolDef`, one on `ToolDescriptor`, one pass-through in
`registerDescriptor`, and a per-tool classification.

## Medium

### Q4. `pcb_manage_layers` destructive actions carry no warning and no backup

`src/bridge-daemon/tools/pcb-layer-tools.ts:22-32`. Two of the ten actions are
destructive:

- `set_copper_count` — reducing a 4-layer board to 2 layers discards the inner
  copper.
- `remove` — deletes a custom layer and whatever is drawn on it.

The description reads "set copper layers (count: 2,4,6,...,32)" and "remove a
custom layer (layer: string)". No irreversibility wording, no backup call.

AUDIT H5 named this action specifically ("`pcb_manage_layers set_copper_count`,
etc. have no backup and no 'irreversible' wording") and the 2026-07-23 addendum
marks H5 **FIXED**. The delete-class tools did get the treatment; this one did
not. The addendum's status is wrong for this item.

### Q5. `EDA_WS_ALLOW_ALL_ORIGINS=1` is an undocumented allowlist bypass

`src/bridge-daemon/index.ts:55`. Setting it makes `isAllowedOrigin` return
`true` for every origin, including no origin at all. It appears in no README,
no AUDIT entry and no doc under `docs/`, and the daemon does not log a warning
at startup when it is set. The only trace is the per-handshake line, which
reports `accepted` exactly as it would for a legitimate origin.

Under the default auth policy (`EDA_WS_AUTH` unset, so a connection that
cannot read the token is accepted on Origin trust) this variable reduces the
WS listener to fully unauthenticated. That is the C4 pre-fix state, reachable
by one environment variable, with no signal to the operator. Origin checking
was never a strong control on a local port, but an undocumented switch that
removes the last stated control deserves a doc line and a loud startup log.

### Q6. MCP server advertises version `1.0.0`

`src/mcp-server/index.ts:61` hardcodes `version: '1.0.0'` in the `McpServer`
constructor. `package.json` and `extension.json` are both `1.5.0`. Clients
surface this in `/mcp` output and in logs, so version reports from the field
will be wrong. Read it from `package.json` (or a generated constant) instead.

### Q7. `sch_modify_component` description hides its two most important facts

`src/bridge-daemon/tools/sch-write-tools.ts:141`: "Modify properties of a
schematic component (position, rotation, designator, etc.)".

Two things a calling model needs and cannot get anywhere else:

1. **The bug-1 guard exists.** Unspecified metadata (`supplierId`,
   `otherProperty`, `manufacturer`, `manufacturerId`, `supplier`, `uniqueId`)
   is snapshotted and merged back, so a position-only edit is now safe. On
   stock EasyEDA it is not. A model that has learned to fear this call from
   upstream documentation will avoid it or wrap it in unnecessary read-back
   verification.
2. **`document` cannot move a component across schematic pages.** README's
   "Not fixed (yet)" section records this, confirmed by catching
   `undefined.getState_ComponentType`. The tool description implies it works,
   because `document` is described generically as "auto-switches to this
   document before executing".

Compare `sch_swap_supplier_part`, whose description does lead with its
limitation. The README is not in the model's context; the tool description is.

### Q8. `refresh: true` can be served by an in-flight stale netlist fetch

`src/extension/handlers/sch-netlist-utils.ts:88-89`:

```ts
if (netlistInflight) return netlistInflight;
```

The check runs after the cache-freshness test but takes no account of
`forceRefresh`. If a fetch started before an edit is still in flight, a
subsequent `refresh: true` call joins it and receives pre-edit data. The
parameter is documented across four tools as "bypass the netlist cache and
force a fresh recompute", so a caller who has just edited the schematic in the
EasyEDA UI and passes `refresh: true` can still get the old netlist.

Related: `invalidateNetlistCache()` (:35) clears `netlistCache` but not
`netlistInflight`, so a write that lands mid-fetch does not cause the in-flight
result to be discarded, and it is then cached as current.

Low probability under the H11 queue, which serialises handlers per tab, but
`sch.component.getAll` deliberately runs the netlist fetch in parallel with the
page walk (`sch-component.ts:245-251`), so intra-request concurrency is real.

### Q9. `sch_swap_supplier_part` matches against unresolved templates

`src/extension/handlers/sch-component.ts:182` calls
`eda.sch_PrimitiveComponent.getAll(undefined, false)` and matches the raw
result. Unlike `sch.component.get` and `sch.component.getAll`, which both call
`resolveComponentTemplates`, the swap path never resolves `={...}` expressions.

EasyEDA stores fields such as `manufacturerId` as template expressions
(`={Manufacturer Part}`) pointing at netlist properties. A caller doing
`match: {manufacturerId: "MP1584EN"}` gets zero matches on any component stored
that way, and a `dryRun` reports "0 swapped" rather than an error. The read
tools' own descriptions state "Template expressions like `={Manufacturer Part}`
are automatically resolved" but the write tool's `match` semantics are
documented as "the same semantics as read-tool filter", which is now untrue in
the way that matters.

### Q10. Fab-export tools carry no DRC-first guidance

`pcb_export` and `pcb_export_to_file`
(`src/bridge-daemon/tools/manufacture-tools.ts`) will happily emit Gerbers,
pick-and-place and ODB++ from a board that has never had DRC run. The
descriptions cover formats, options and payload size, and say nothing about
verification.

This is the single most consequential ordering constraint in the whole
workflow, and it is exactly the kind of thing a model will skip when nothing
tells it not to. It is also the point at which the fork's own history is
instructive: the bug-4 dead-copper defect passed clearance DRC and was only
caught by a No-Connection check, so "run DRC" needs to be "run DRC including
the connectivity checks". A sentence in each description, pointing at
`pcb_run_drc` and at the pcb-lint skill, costs nothing.

### Q11. Daemon-side dispatch performs no input validation

`ToolRegistry.dispatch` (`src/bridge-daemon/registry.ts`) looks the tool up by
name and calls `entry.def.handler(args)` directly. The zod shape is used only
to generate the JSON Schema descriptor.

Validation therefore happens exclusively in the MCP server process, via
`fromJSONSchema` re-hydration of a JSON Schema that was itself generated from
zod. That round trip is lossy for anything JSON Schema cannot express (the
registry passes `unrepresentable: 'any'` precisely because of this), so
refinements do not survive. Any other UDS client, and the daemon's own
`bridge_restart` path, bypasses validation entirely.

Carried over from the AUDIT nice-to-have list; still open, and now worth
raising because handler bodies index into lookup maps by `action` string.

### Q12. `lib_symbol_update_document_source` has no backup and no warning

`src/bridge-daemon/tools/lib-tools.ts:160`. It replaces a library symbol's
entire `.esym` source. `lib_symbol_delete` (:129) and `lib_device_delete`
(:247) are both explicit: "IRREVERSIBLE: no undo, and no backup snapshot is
taken (library assets are not documents). Fetch and save the symbol source with
`lib_symbol_get` first". A full-source overwrite destroys just as much and says
none of it. Straight consistency fix on the description.

## Low

### Q13. Documentation drift

- `README.md:79` and `README.md:120` both say **84 tests**; the suite is **127**.
- `README.md:135` says **~98 tools**; the registry advertises **100**.
- `HANDOVER-2026-07-23.md:36` says "`npm test` — 107 tests (**vitest**)". The
  runner is `node --test` with `ts-node/register` (see the `test` script in
  `package.json`). A Sonnet session following that handover would reach for
  vitest and find nothing.

### Q14. `syncToolList` treats the tool name as identity

`src/mcp-server/index.ts:88-99`. On daemon reconnect, an already-registered
name is skipped, so a daemon upgrade that changes a tool's schema or
description keeps the stale registration until the MCP client restarts. The
comment acknowledges this. It matters more once annotations land (Q3), because
a corrected `destructiveHint` would not propagate. A descriptor hash comparison
is a few lines.

### Q15. Backup repo has no retention policy

`src/bridge-daemon/backup.ts` commits a full project snapshot on every
`project_import_file` and a full document on every destructive doc write, into
`~/.easyeda-mcp-backup`, forever. `gc.auto 256` is configured, which packs
objects but never drops history. On a project the size of Splitflap the repo
grows without bound and nothing warns the user. A documented pruning command,
or an age or count cap, would close it. Current hardware-VCS guidance is
consistent on this point: archive or delete obsolete versions rather than
keeping every snapshot indefinitely.

### Q16. `_availableFields` is derived from the first item only

`src/extension/ws-client.ts:111`:
`const availableFields = items.length > 0 ? Object.keys(items[0]) : []`.

On a heterogeneous array (mixed component types, primitives of different
shapes) this under-reports the fields a caller could project. Since the
`fields` parameter description tells models to always specify fields, an
incomplete `_availableFields` actively misleads. Union the keys across a bounded
sample instead.

## Best-practice sweep — what the field says, and where this MCP sits

Sourced 2026-07-24. Only the points that bear on this codebase.

### MCP and agent-safety practice

| Practice | Status here |
|---|---|
| Tool annotations (`readOnlyHint` / `destructiveHint` / `idempotentHint`) classify risk on the descriptor, not in prose | **Absent** (Q3) |
| Destructive and irreversible operations require a human checkpoint | Partly: honest prose on deletes, nothing machine-readable |
| Tool schema quality dominates server quality | Strong. Enum-constrained actions, `describe()` on nearly every field, context-budget params (`fields`/`filter`/`limit`) |
| Minimum necessary data returned | Strong. `fields` projection and `skipNetlist` are both genuine context savers |
| Validate at the boundary, not just at the client | **Gap** (Q11) |
| Prompt injection is the top LLM-application risk | Handled where it counts: extension log lines are stripped of CR/LF and capped (`index.ts:335-339`), commit messages sanitised (`backup.ts:38`), `instanceId` shape-validated |

The tool descriptions in this fork are, on balance, better than most MCP
servers I have read: the units note (`PCB_COORD_NOTE`), the `$`-prefixed net
explanation in `sch_get_connectivity`, and the upstream-bug warnings on
`pcb_manage_rule_config` are the sort of hard-won detail that only comes from
using the thing. The gap is that none of it is machine-readable risk metadata.

### PCB and EDA engineering practice

| Practice | Status here |
|---|---|
| Run ERC before layout, DRC during and after routing, and re-run before fab output | Tools exist (`sch_run_drc`, `pcb_run_drc`); **no ordering guidance in descriptions** (Q10) |
| ERC and DRC passing does not guarantee a good board; a wrong divider ratio or missing pull-up is invisible to both | Covered outside this repo, by the pcb-lint skill (SCH-08 regulator Vout, SCH-09 driver COM, SCH-10 USB-C CC) |
| Compare schematic against layout after ECOs | `sch_import_changes` / `pcb_import_changes` exist; no LVS-style comparison tool and no guidance |
| Annular ring 0.15 mm minimum, 5–6 mil target for drill-registration margin | pcb-lint `pcb_08_annular_ring.py` |
| Solder mask expansion 0.05–0.1 mm, 0.2 mm minimum dam | pcb-lint `pcb_14_soldermask_expansion.py` |
| Version-control design data; keep a recoverable pre-edit state | Strong, and unusual: the git-backed backup repo is a genuine differentiator. Undermined by the Q2 hole and the Q15 unbounded growth |
| AI handles roughly 80% of execution; humans keep specification, review and manufacturing-risk judgement | Matches the fork's own posture. Worth keeping explicit in the README |

The domain coverage is good. The two real gaps are ordering guidance at the
fab-export boundary (Q10) and the absence of any schematic-versus-layout
consistency check, which the sources single out as the thing ECOs quietly
break.

## Recommended order of attack

1. **Q1** — document-switch verification. Silent wrong-board writes, and the
   guard pattern already exists in this repo.
2. **Q2** — backup `sch_swap_supplier_part`. One call, closes the last
   unbacked bulk mutation.
3. **Q3** — tool annotations. Mechanical, touches 100 tools, high leverage,
   and cheapest to do before anything else edits the descriptors.
4. **Q4, Q7, Q10, Q12** — description and warning fixes. One commit.
5. **Q8, Q9** — netlist freshness and template resolution in the swap path.
6. **Q5, Q6, Q13** — documentation and version hygiene.
7. **Q11, Q14, Q15, Q16** — the remaining medium and low items.

Items 1 to 6 are scoped as work packages in
[`HANDOVER-2026-07-24.md`](HANDOVER-2026-07-24.md).
