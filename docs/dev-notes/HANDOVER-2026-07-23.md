# Block A — fork fixes (this repo, one version bump)

## WP1. Security: pin the auth-challenge token path client-side

**The highest-value fix in this work order.** The C4 auth challenge, as
shipped, is an arbitrary-file-read primitive.

- `src/extension/ws-client.ts:320` — on an `auth.challenge` message the
  extension calls `answerAuthChallenge(extensionUuid, String(request.tokenPath || ''))`.
- `src/extension/ws-client.ts:454-457` — `answerAuthChallenge` reads
  **whatever path the server sent** via
  `eda.sys_FileSystem.readFileFromFileSystem(tokenPath)` and returns the file
  contents over the socket.
- Attack: the daemon idle-exits shortly after the last MCP client disconnects,
  and the extension retries its connection every 15 s. Any local process that
  binds port 16168 during a gap gets a connection from the real extension,
  sends `auth.challenge` with `tokenPath: "/Users/<user>/.ssh/id_ed25519"`
  (or any user-readable file), and receives its contents.

**Fix:** validate the server-sent path before reading. The extension cannot
compute the daemon's exact state dir (`src/bridge-daemon/protocol.ts:6-8`
allows an `EDA_BRIDGE_STATE_DIR` override the extension cannot see), so
validate shape instead of equality:

1. Reject any path containing `..` or a null byte.
2. Require basename exactly `ws-token` AND parent directory basename exactly
   `.easyeda-mcp` (matches `wsTokenPath()` in
   `src/bridge-daemon/protocol.ts:24-26`).
3. On rejection: do NOT read anything; respond with the existing
   "could not read the token file" auth answer (the daemon already handles
   that case at `src/bridge-daemon/index.ts:491-494`) and log a warning with
   the offending path. This closes the file-read primitive; the rogue server
   learns nothing.

Note the trade-off in a comment: an `EDA_BRIDGE_STATE_DIR` override whose
directory is not named `.easyeda-mcp` will fail hardened auth by design.

**Tests:** `tests/bridge-daemon.test.ts` already has four C4 auth tests. Add:
rogue path (`/etc/passwd`, `~/.ssh/...`, traversal) is refused with no read
attempt; happy path (`.../.easyeda-mcp/ws-token`) still verifies. The
validator should be a pure exported function so it is testable without a
WS session.

## WP2. Buffered-response id collision across daemon restarts

- `src/bridge-daemon/index.ts:134-136` — `extRequestIdCounter` produces ids
  `d1`, `d2`, ... and resets to 0 every daemon run.
- `src/extension/ws-client.ts:400,416,425` — while disconnected the extension
  buffers responses (`bufferResponse`, bounded at 100) and flushes them on
  reconnect (`flushBufferedResponses`, called at :530).
- Failure: daemon restarts, issues a fresh `d5` for a new unrelated request;
  the extension flushes a stale buffered response for the OLD `d5`; the
  daemon's `p.ws === ws` check passes (both are post-reconnect sockets) and
  the stale payload is accepted as the answer.

**Fix:** include a per-run nonce in the id, e.g.
`d${runNonce}-${++extRequestIdCounter}` where `runNonce` is a short random
hex string generated once at daemon startup. Stale ids then never match.
Check the id-recovery regex in `src/bridge-daemon/diag.ts` (H13 work) still
extracts the new format, and grep for any other code that parses id shape.

**Tests:** unit test that two daemon "runs" (two nonces) cannot cross-resolve.

## WP3. H11 queue force-release lapses serialisation

- `src/extension/ws-client.ts:255` — `QUEUE_SLOT_TIMEOUT_MS = 120_000`. The
  per-tab request queue force-releases a slot after 120 s so a wedged handler
  cannot deadlock the extension.
- Failure: the wedged handler is not cancelled; when it eventually completes
  it acts against whatever document is active THEN (a later request may have
  switched tabs), and may send a late response. The serialisation guarantee
  lapses exactly in the hang cases the queue was built for.

**Fix:** epoch/generation guard. Each queue slot gets a generation number;
force-release increments it. The queued pipeline re-checks its captured
generation at its resume points (after the document switch, before invoking
the handler, before sending the response); on mismatch it abandons: no
document mutation, no response (or an explicit error response), one log line.

**Tests:** simulate a slow handler + force-release + a second request; assert
the first handler's late completion neither mutates state nor answers.

## WP6. SCH-08: regulator Vout vs downstream Vmax (top priority)

This check exists to prevent recurrence of the worst incident on record:
Splitflap-v2 Board1 shipped with an MP1584 FB divider (68k/15k) producing
4.43 V into an ESP32-C3 rated 3.6 V absolute max; caught only by manual
datasheet review AFTER boards were ordered. `SKILL.md` step 3b (line ~51)
currently enforces this manually every run; your job is to automate it.

Logic:
1. Identify adjustable regulators in the BOM (part-number table: start with
   MP1584 (Vref 0.8 V), and make the table data-driven so new parts are one
   row; unknown adjustable regulator = WARN "Vref unknown, verify datasheet",
   never silently pass).
2. From the netlist, find the FB divider: R_upper between VOUT net and FB
   pin, R_lower between FB and GND.
3. Vout = Vref × (1 + R_upper/R_lower), from the ACTUAL resistor values.
4. Collect downstream ICs on the VOUT net; compare against an abs-max table
   (same data-driven approach; ESP32-C3 = 3.6 V).
5. **HARD ERROR** if Vout > any downstream abs max. WARN if Vout deviates
   >10% from the rail's design-intent voltage (from net name, e.g. +3V3).

The check runs on netlist/BOM data structures like the other SCH checks; keep
datasheet lookups as static tables in the module, flagged clearly as
data-to-verify. After it lands, update `SKILL.md` step 3b to point at the
automated check, keeping the manual procedure as fallback wording for boards
with parts missing from the tables.

## WP7 (stretch). SCH-09 and SCH-10

- **SCH-09, driver COM pin**: if the BOM contains ULN2003/TPL7407 variants,
  the COM pin's net must be the motor supply rail (not floating, not GND):
  the COM pin is the flyback-diode common cathode; floating = dead driver on
  first inductive kick. TPL7407L extra: WARN if the COM rail is below 6.5 V
  (feeds the internal gate regulator). Source: TI TPL7407LA datasheet.
- **SCH-10, USB-C sink CC resistors**: if the BOM has a USB-C receptacle,
  require a 5.1 kΩ resistor to GND on EACH of CC1 and CC2, two separate
  resistors. One shared or missing = no VBUS from any C-to-C cable or USB-C
  charger. Source: Infineon KBA Rp/Rd/Ra.

Full sourced rationale for both is in the memory file
`reference_pcb_best_practices.md` (Gate 1, "Driver / interface must-checks")
if reachable; otherwise the descriptions above are self-sufficient.
