# Block A — correctness and data safety (do these first)

## WP1. Verify the document switch actually landed (Q1)

**The highest-value fix in this work order.** A silently failed document
switch sends every subsequent write to the wrong board.

- `src/extension/ws-client.ts:355-359` — the queued pipeline does
  `await switchToDocument(document)` and discards the result.
- `src/extension/ws-client.ts:220-243` — `requireDocumentType(method)` is the
  only post-switch gate. It checks `documentType` (1 = schematic, 3 = PCB) and
  nothing else, so two PCBs in the same project are interchangeable to it.
- `src/extension/handlers/sch-page-walk.ts:14-17` and `:38-43` — this repo
  already documents that `openDocument` can fail while leaving the previous
  document active, and already guards it by re-reading the active page and
  throwing on mismatch. Copy that pattern.

Failure mode to fix: a project holding Board1/Board2/Board3 (see the comment
at `src/extension/handlers/sch-component.ts:191-193`). A request for Board 3's
PCB whose open silently no-ops leaves Board 1 active; the type gate passes;
`pcb_delete_primitives` runs against Board 1. The daemon-side backup snapshots
whatever document it *thinks* is active, so it does not protect the board that
actually changes.

**Fix:**

1. Add a pure exported helper, e.g.
   `src/extension/active-document-check.ts`, with a function that takes the
   requested `document` string and the object returned by
   `dmt_SelectControl.getCurrentDocumentInfo()` and returns
   `{ ok: true } | { ok: false, reason: string }`.
   - The requested value may be a bare `itemUuid` or `itemUuid@suffix` (see
     `switchToDocument` at `ws-client.ts:276-302`).
   - `getCurrentDocumentInfo()` exposes both `uuid` and `tabId`.
     `handlers/editor.ts` (`editor.getOpenTabs`) already relies on
     `tab.tabId.startsWith(activeUuid)`, so match on that relationship:
     accept when `tabId === document`, or when `document`'s pre-`@` segment
     equals `uuid`.
   - Be permissive when the info object is missing a field entirely (return
     `ok: true` with a note) rather than breaking older EDA Pro builds. Log
     the permissive case via `bridgeLog`.
2. Call it in `handleMessage` immediately after the `switchToDocument` await,
   before the `isForceReleased()` check that follows. On failure, respond with
   an error naming both the requested and the actual document, and do not run
   the handler.
3. Symbol and footprint editor documents (`doctype` 2 and 4 in
   `switchToDocument`) go through `lib_Symbol.openInEditor` /
   `lib_Footprint.openInEditor`, which may not surface the same identity
   fields. Verify behaviour there; if identity is unavailable, fall through to
   the permissive path with a log line rather than failing the request.

**Tests:** new `tests/active-document-check.test.ts`. Cover: exact `tabId`
match, bare-uuid match against `uuid@suffix`, mismatch (two different PCB
uuids, both documentType 3, must fail), missing `tabId`, missing `uuid`,
missing info object, and empty-string `document`.

# Block C — netlist freshness and the swap filter

## WP8. `refresh: true` must not join a stale in-flight fetch (Q8)

`src/extension/handlers/sch-netlist-utils.ts:88-89`:

```ts
if (netlistInflight) return netlistInflight;
```

The in-flight coalescing check ignores `forceRefresh`, so a caller who has just
edited the schematic in the EasyEDA UI and passes `refresh: true` can be handed
pre-edit data by a fetch that started earlier. The parameter is documented on
four tools as "bypass the netlist cache and force a fresh recompute".

Related: `invalidateNetlistCache()` (:35) clears `netlistCache` but not
`netlistInflight`, so a write landing mid-fetch does not invalidate the result
that fetch is about to cache.

**Fix:** track a generation counter alongside the in-flight promise. Increment
it in `invalidateNetlistCache()`. A `forceRefresh` call, or a call whose
captured generation no longer matches, starts a new fetch rather than joining
the existing one; a completed fetch only writes to `netlistCache` if its
generation is still current. Keep the coalescing benefit for the common case
(two non-refresh reads firing together, which `sch.component.getAll` does
deliberately at `sch-component.ts:245-251`).

**Tests:** the module imports `eda` globals, so extract the
generation/coalescing decision into a pure helper if that is cheap, and test
that. If it is not cheap, keep the change small and covered by review; do not
build a global `eda` mock for this alone.

## WP9. Resolve templates before matching in `sch_swap_supplier_part` (Q9)

`src/extension/handlers/sch-component.ts:182`. `processPage` calls
`eda.sch_PrimitiveComponent.getAll(undefined, false)` and matches the raw
result. `sch.component.get` (:223-236) and `sch.component.getAll` (:238-279)
both call `resolveComponentTemplates` first; the swap path does not.

EasyEDA stores fields such as `manufacturerId` as `={Manufacturer Part}`
template expressions. A caller doing `match: {manufacturerId: "MP1584EN"}`
therefore gets zero matches on any component stored that way, and `dryRun`
reports `swappedCount: 0` rather than an error, which reads as "nothing
matched" instead of "the filter could not see the data".

**Fix (preferred):** fetch the parsed netlist once before the page walk and
call `resolveComponentTemplates(c, netlist)` on a **copy** of each component
before `matchesFilter`. Do not mutate the object you then pass to
`preserveMetadataOnModify` — the write must carry the raw stored values, not
resolved ones, or you will bake resolved literals into components that
intentionally template their fields. This is the subtle part of the work
package; comment it.

**Fix (fallback, if the netlist fetch proves too slow inside the walk):** leave
the behaviour and add one line to the tool description stating that `match`
runs against stored values, so fields stored as `={...}` templates will not
match their resolved text, and that `sch_get_all_components` shows the resolved
values for comparison. Tell Ben which option you took and why.

**Tests:** `tests/component-match.test.ts` already covers `matchesFilter`
directly. Add cases there for a component whose field is a template string, in
both the resolved and unresolved forms, so the intended semantics are pinned
whichever option you take.

# Block E — deep-pass findings (D-series)

## WP11. Mutual auth: the extension must verify the daemon (D1)

**The highest-value security fix in this work order.** The C4
challenge-response authenticates the extension to the daemon only. The
extension auto-reconnects to `ws://localhost:16168` every 15 s
(`src/extension/ws-client.ts:602-635`) and executes whatever
`{id, method, params}` arrives against the full `allHandlers` surface
(`ws-client.ts:150-169`). The daemon idle-exits 5 s after the last MCP client
disconnects, so daemon-down windows are routine; TCP loopback ports carry no
user identity, so **any account on the machine** can bind 16168 during one
and then read (`fileManager.getDocumentSource`,
`fileManager.getProjectFileByUuid`) or corrupt
(`fileManager.setDocumentSource`, skipping every daemon-side backup) the
user's open designs. Bonus flaw: the current answer sends the **raw token**
to the unverified peer.

**Fix — HMAC mutual challenge, raw token never on the wire:**

1. Daemon challenge becomes
   `{type: 'auth.challenge', tokenPath, scheme: 'hmac-v1', serverNonce}`
   (`src/bridge-daemon/index.ts:530`). `serverNonce` = fresh
   `randomBytes(16).toString('hex')` per connection.
2. Extension (`answerAuthChallenge`, `ws-client.ts:482-500`): keep the WP1
   path validation exactly as is. Read the token. Generate `clientNonce`
   (`crypto.getRandomValues`). Answer
   `{type: 'auth', data: {scheme: 'hmac-v1', clientNonce, mac}}` where
   `mac = HMAC-SHA256(key = token, msg = "ext|" + serverNonce + "|" + clientNonce)`,
   computed with `crypto.subtle` (renderer context has WebCrypto). If the
   token cannot be read (browser build, permission off), answer
   `{token: null}` as today.
   **If the challenge has no `scheme` field, do NOT fall back to sending the
   raw token — answer `{token: null}` and `bridgeLog` it.** This kills raw-token
   disclosure to rogue listeners. (Consequence: a new `.eext` against an old
   daemon runs on Origin trust until the daemon is upgraded; fine by default,
   breaks only `EDA_WS_AUTH=require` during partial upgrades — note it in the
   README line you add.)
3. Daemon: verify the ext MAC with `node:crypto` `createHmac` +
   `timingSafeEqual` (replacing `tokenMatches` for hmac-v1 answers; keep the
   legacy raw-token path so an OLD `.eext` against a NEW daemon still
   authenticates). On success reply
   `{type: 'auth.ok', mac: HMAC-SHA256(token, "daemon|" + clientNonce + "|" + serverNonce)}`.
   Domain-separated prefixes ("ext|"/"daemon|") prevent reflection.
4. Extension: on `auth.ok`, verify the daemon MAC against the token it read.
   On success, mark the connection daemon-verified. On failure or absence
   (and the token WAS readable): show a one-time warning toast
   ("Connected to an unverified bridge daemon") via
   `eda.sys_Message.showToastMessage`, `bridgeLog` it, and keep current
   behaviour otherwise — gating handlers on verification is a follow-up
   decision for Ben, not this WP.
5. Extract MAC construction into a pure, testable module shared by tests
   (e.g. `src/extension/auth-mac.ts` mirroring a daemon-side helper — the
   string-building must match exactly; write one cross-check test that
   computes both sides from the same inputs).

**Tests:** extend `tests/bridge-daemon.test.ts` (it already stands up a real
daemon WS): hmac-v1 handshake succeeds end to end; wrong ext MAC closes the
socket; extension helper refuses to produce a raw-token answer when the
challenge lacks `scheme`; daemon MAC verification rejects a reflected ext
MAC. Unit-test the pure MAC module for the domain separation.

## WP12. Transport efficiency: stop double-parsing and triple-shipping (D2 + D3)

Two independent small fixes, one commit.

**D2 — double parse:** `src/bridge-daemon/index.ts:479-503` runs
`tryParseAuthToken(raw)` (a full `JSON.parse`) on every message while
`authed` is false — which, in the default posture (browser EasyEDA or desktop
without the external-interaction permission), is forever. Multi-MB
document-source responses get parsed twice on the daemon thread. Fix: the
extension sends exactly one auth answer per challenge, so after the first
message `tryParseAuthToken` recognises (correct, wrong, or null), set an
`authAnswered` flag and skip the probe branch. Wrong tokens still close the
socket; `EDA_WS_AUTH=require` behaviour unchanged. If you land WP11 first,
fold this flag into its handshake state machine rather than adding a second
one.

**D3 — triple ship:** `document_set_source`
(`file-manager-tools.ts:132-153`) fetches the full source once for context
(discarding the source), again inside `backupDocument` (`backup.ts:153`),
then sends the new source — three full-document WS crossings and three H11
queue slots per upload; `document_load_from_file` (:200-220) is identical.
Fix: give `backupDocument` an optional
`prefetched?: { source: string; context: DocumentContext }` param that skips
its own fetch, and thread the step-1 result through from both tools. Also
tightens the window in which another client's request can interleave between
backup and write. Keep `backupDocument`'s behaviour byte-identical when the
param is absent (the delete tools still call it bare).

**Tests:** `backup.ts` is exercised via mocked `ToolContext` patterns — if a
harness for that is more than ~40 lines, unit-test only that `backupDocument`
with `prefetched` does not call `sendToExtension`, via a stub ctx that
records calls.
